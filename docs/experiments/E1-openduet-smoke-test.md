# E1 — OpenDuet + OpenCore smoke test (P0)

Status: **key built, physical test PENDING** · Date: 2026-11-19

## Question

Does an unmodified OpenCore 1.0.7 RELEASE OpenDuet chain, installed by our own guarded tooling
(not `BootInstall*.tool`), reach the OpenCore picker and the UEFI Shell on a BIOS-only reference machine?

Out of scope: booting any OS.

## Protocol (any BIOS-only test machine; written for the Dell, run on the Aurora R1)

1. Plug the key into a rear USB port. Power on, press **F12**, choose the USB storage entry.
2. Note what appears and where it stops (photo of the screen if it stops).
3. Expected: OpenCore text picker with at least **UEFI Shell**. It waits (no timeout).
4. Select **UEFI Shell**. Type `ver`, then `map -r`, take a photo. Type `reset -s` to power off.
5. **Do not** start any OS entry the picker may list (out of scope for E1).
6. Bring the key back: the OpenCore log `opencore-*.txt` written at the key's root is the evidence.

## Results

### Run 1 — 2026-11-19 — Alienware Aurora R1 (not the Dell)

The owner ran the key on an **Alienware Aurora R1** (Core i7, X58 platform — exact CPU/BIOS to record),
a machine of the same generation as the golden reference.

- Reached: **OpenCore picker** — `OpenCore Boot Menu (REL-107-2026-03-20)`, text picker, full-HD text
  console. Entries: `L2U-E1 (external)`, `NO NAME` (unidentified, probably an internal volume), `UEFI Shell`.
  So BIOS → boot0 → boot1f32 → OpenDuet → OpenCore works on this machine, and OpenDuet sees the USB key.
- Blocked: **USB keyboard does not respond** in the picker → UEFI Shell not reached.
- Config on the key: `OpenRuntime` + `Ps2KeyboardDxe`, `KeySupport=true` (Sample default).
- OpenCore log: `opencore-2026-11-19-183359.txt` collected (copy in `build/key-logs/`): 262 144 bytes,
  **all zero** — file preallocated but nothing flushed (run ended in the picker / power-off). Timestamp
  18:33 vs 19:33 local suggests the RTC is in UTC. Logging must be fixed before the log can serve as evidence.
- OpenDuet created an `NVRAM/` folder on the key (emulated NVRAM; write stays on the key — consistent with ADR-0005).
- Evidence: owner's screenshot of the picker (to be added to `tests/evidence/`).

Interpretation (hypothesis, not proven): OpenDuet provides USB host + mass-storage drivers but no USB
HID keyboard driver; with only `Ps2KeyboardDxe`, a USB keyboard has no driver.

### E1b — keyboard variants (prepared, not yet tested)

`ocvalidate` 1.0.7 rules found while preparing the fix:
- `OpenUsbKbDxe.efi` and `Ps2KeyboardDxe.efi` must **never** be enabled together;
- `Ps2KeyboardDxe.efi` requires `UEFI/Input/KeySupport = true`.

Two staged variants (`make-test-config.ps1 -Keyboard Usb|Ps2`), both `ocvalidate`-clean:
- **USB**: `OpenRuntime` + `OpenUsbKbDxe`, `KeySupport=false` → for the Aurora R1 run 2.
- **PS/2**: `OpenRuntime` + `Ps2KeyboardDxe`, `KeySupport=true` → equivalent to run 1, for the Dell with a PS/2 keyboard.

### Run 2 — 2026-11-19 — Alienware Aurora R1, E1b USB-keyboard variant

Config: `OpenRuntime` + `OpenUsbKbDxe`, `KeySupport=false`. USB keyboard (port/controller not recorded).

- **USB keyboard works** in the picker and in the Shell.
- **UEFI Shell reached**: `UEFI Interactive Shell v2.2`, `EDK II`, `UEFI v2.70 (Acidanthera, 0x00010010)`.
- `map -r` (read-only enumeration):

| Map | Device path | Reading |
|---|---|---|
| FS0 / BLK1 | `PciRoot(0x0)/Pci(0x1A,0x7)/USB(0x5,0x0)/HD(1,MBR,0x00000000)` | the L2U-E1 key: EHCI controller at 00:1A.7, port 5, MBR partition 1 |
| BLK0 | `…/Pci(0x1A,0x7)/USB(0x5,0x0)` | the key, whole disk |
| FS1 / BLK3 | `PciRoot(0x0)/Pci(0x1F,0x2)/Sata(0x3,0xFFFF,0x0)/HD(1,GPT,85085B13-…)` | internal SATA disk on port 3, GPT partition 1 with a FAT filesystem — most likely an ESP; probably the picker's `NO NAME` entry (to confirm) |
| BLK2 | `…/Pci(0x1F,0x2)/Sata(0x3,0xFFFF,0x0)` | that internal disk, whole |
| BLK4 | `…/Sata(0x3,0xFFFF,0x0)/HD(2,GPT,6CDD1322-…)` | GPT partition 2, no filesystem driver loaded (likely the OS partition: ext4/btrfs/NTFS) |

Findings:
- OpenDuet drives the EHCI controller, USB mass storage and (with OpenUsbKbDxe) a USB keyboard on this X58/ICH-class machine.
- OpenDuet drives the chipset SATA controller (00:1F.2) and reads GPT; internal disk visible read-only.
- Run-2 log `opencore-2026-11-19-184225.txt` is also 262 144 bytes, all zero. Probable cause: Sample's
  `Misc/Debug/DisplayLevel = 0x80000002` logs errors/warnings only, so an error-free boot writes nothing.
  Fix staged and put on the key: `DisplayLevel = 0x80000042` (adds DEBUG_INFO); `ocvalidate` clean.
  Both empty logs kept in `build/key-logs/` and removed from the key. `NVRAM/` on the key is empty.
- **ADR-0006 condition met on one machine** (Aurora R1, one USB keyboard). Still to check: a USB keyboard behind a
  USB 1.1 (UHCI) port, and the Dell.

Evidence: `tests/evidence/alienware-aurora-r1/2026-11-19/run1-opencore-picker.png`, `run2-uefi-shell-map.png`.

Status: Aurora R1 = **EXPERIMENTAL** (bridge reaches UEFI Shell with USB keyboard; no OS booted). Dell = not yet run.

### Run 3 — 2026-11-20 — Alienware Aurora R1, two USB keys

- A second USB key was plugged in: picker lists `VTOYEFI (external)`, `L2U-E1 (external)`, `NO NAME`, `UEFI Shell`.
  `VTOYEFI` is the EFI partition of a **Ventoy** key: `FS0 = …/Pci(0x1A,0x7)/USB(0x2,0x0)/HD(2,MBR,0x1F42B0A4)`.
  OpenDuet enumerates two USB mass-storage devices on the same EHCI controller.
- `ls fs1:\EFI` listed **our own key** (`BOOT`, `OC`), not the internal disk: with a second key the `fsN`
  numbering shifted (internal ESP became `FS2`). Lesson: identify volumes by device path (`Sata(…)` = internal),
  never by `fsN` number.
- Log `opencore-2026-11-20-071939.txt`: still 262 144 bytes, all zero, despite `DisplayLevel = 0x80000042`.
  OpenCore manual (Misc → Debug): `DEBUG_INFO` (0x40) exists only in DEBUG/NOOPT builds; RELEASE logs only
  WARN/ERROR. An error-free RELEASE boot therefore writes nothing — consistent with all three runs.
  Fix: use the OpenCore **DEBUG** build for experiments (not yet downloaded), optionally with on-screen logging (Target bit 0x02).
- Screenshots: `tests/evidence/alienware-aurora-r1/2026-11-20/`.
